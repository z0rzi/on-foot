## Field findings — what the device still tells us

**FIELD-1 — the system kills the app in the background** · should-fix, open, and the most
interesting thing left. Every data point says **memory, not CPU**: the one excessive-CPU kill was
~3.9% against a 2% cap, while the footprint runs 474-512 MB pss / 595-624 MB rss across every
sample.

The finding has now been redirected twice by evidence. Its original question — what burns CPU while
cached — was wrong. The second answer, "it tracks what a *recording* retains", is **also wrong**:
`dumpsys meminfo` on 2026-10-07 at 16:23, with the app merely showing a map and **not recording**,
read 474 MB pss / 595 MB rss — Native Heap 199 MB, Graphics 125 MB, Dalvik 15 MB. A recording adds
only tens of MB on top of that.

So the bulk is the map SDK's tiles and textures, resident whenever the map is open, and `livePoints`
is no longer the first suspect. Next step: sample `meminfo` with the map closed (on the Trails or
Settings tab) to separate the map's share from the rest, and check whether Mapbox's tile cache is
bounded in this app's configuration.

**FIELD-3 — the interruption toast is hidden, and its range overstates the gap** · minor, open, and
cheap now. The toast fires behind the splash, and its range starts at the last stored point rather
than the gap's real start. The debug log records the announced range, so a fix can be checked against
real field data instead of a guess.

**FIELD-5 — a crash in a relaunched recording process can hang instead of dying** · open, seen once,
unconfirmed. Ironically harder to reproduce now that `FIELD-4` — the crash that produced it — is
fixed.

`FIELD-2` (vanishing recording sheet) and `FIELD-4` (permission-revoke crash) are both closed and
device-verified.

## Error handling — four open, none in the backlog table

**ERR-7 — a deleted trail leaves a permanently dangling `linked_trail_id`** · should-fix, S.
`schema.ts:21,41` declares the column as a plain `integer` on both `activities` and
`recording_sessions` — no foreign key, no `ON DELETE SET NULL` — and `trailsRepository.ts:26-28`'s
`deleteTrail` removes only the trail row. So the link is stuck forever, and the loaded-entity hook
now writes a `warn` every time that activity's sheet opens. Repeating benign noise is what degrades
the debug log. Fix: null the column in `deleteTrail`, or add the FK and let SQLite enforce it.

**ERR-6 — `metricsForSegments` runs outside the surrounding `try`** · should-fix, S.
`app/trail/new.tsx:50` sits after the `try`/`catch` at `:33-47` closes, so a throw there is an
unhandled rejection behind a spinner that never exits — `ERR-3`'s defect class, in a file the
loaded-entity work touched. Deliberately not folded into that `try`: it would report "Not a GPX
file" for something that is not a parse failure. Fix: a third outcome in the same effect.

**ERR-5 — unhandled picker rejection** · minor, S. `trails.tsx:68-77`'s `pickGpx` is an async
`onPress` that can reject (an eslint attribute exemption hides it), and `:27`'s `void loadTrails()`
on focus is the same shape with no failure outcome.

**ERR-4 — silent no-ops** · minor, S. Tapping an activity during a recording returns with no
feedback; a failed offline-registry `init` leaves the settings list saying "No offline maps yet"
until the app restarts, because `OfflineMapsList` reloads trails on focus but never re-`init`s.

## Proposed work — not from the review

- **Progressive route rendering** · proposed by the owner 2026-10-07, after measuring a 13.3 km trail
  selection at 657 ms of frame activity. Show the trace on the map immediately as a plain line, then
  let the profile, the slope colours and the elevation graph arrive a beat later. It works because
  Mapbox draws on the native thread: once JS hands over the plain coordinates the map can paint while
  JS is still deriving. **Item 7 is done** (`28d1e44`), so this is no longer a prerequisite to wait
  on: `useRouteDisplay` is now the one place three places used to derive the profile independently,
  so deferring it is one change and everything downstream appears together. Likely idiom:
  `useDeferredValue(segments, null)` (the two-argument form is present in React 19.2.3's types —
  checked). **Measure before designing**: the 657 ms is at least two costs — the `JSON.parse` of the
  whole track, which deferral cannot help, and the profile/banding arithmetic, which it can. The
  split is unknown, and if the parse dominates this buys less than it looks. That measurement is now
  cheap, because `useRouteDisplay` is the single place to instrument. **Open design question**: on a
  short route the derivation is already fast, so deferring could add a flicker where today it is
  instant — probably wants a size threshold, which needs its own device verification. Gets its own
  spec.

## Standing obligations

Every patched Expo module must appear in `package.json` → `expo.autolinking.android.buildFromSource`,
transitively, or its patch is a silent no-op in the APK. Source-building the three listed modules
costs ~13 min a release build. Verify a build took a patch by grepping its dex for `[onfoot-patch]`
before trusting a device result. Full detail in `docs/architecture/native-patches.md`.

Device verification is the user's step and is never claimed on their behalf.
