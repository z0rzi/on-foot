# Native patches

Two Expo modules and one JS library are patched with `patch-package`. `postinstall` applies them all,
so a fresh `npm install` is enough — but a patch is invisible debt: it silently stops applying when the dependency
moves. **Each entry here says what breaks if the patch is dropped, so the next person upgrading knows
what to re-test.**

The two Expo patches are to Android native sources in `node_modules`, and `android/` itself is
generated by `npx expo prebuild` and gitignored. The `@gorhom/bottom-sheet` patch is to TypeScript
source, which Metro bundles directly (the package's `react-native` field points at `src/`), so the
native build notes below do not apply to it.

## A patched Expo module is NOT compiled unless you say so

**Expo 57 ships its own Android modules as prebuilt AARs.** Each package carries one at
`node_modules/<module>/local-maven-repo/…/<artifact>-<version>.aar`, declared by a `publication` block
in its `expo-module.config.json`, and Gradle resolves *that* instead of compiling `android/src`. A
`patch-package` patch to the module's Kotlin then applies cleanly to `node_modules`, survives
`postinstall`, and **changes nothing in the APK** — which is exactly what happened on 2026-10-02 and
again on 2026-10-04, when a build made from patched source kept crashing at upstream's line number.

The opt-out is an autolinking option, in `package.json`:

```json
"expo": { "autolinking": { "android": { "buildFromSource": ["expo-location", "expo-task-manager"] } } }
```

Each entry is a regex matched in full against the Gradle project name (`expo-location`, not
`host.exp.exponent:expo.modules.location`). It drives `forceBuildFromSource` in autolinking's settings
plugin, which forces `shouldUsePublication = false` and makes Gradle compile the module from
`node_modules/<module>/android`.

**So: every patched module must also be listed in `buildFromSource`.** Adding a patch without it is a
silent no-op.

**The list is transitive.** A module built from source resolves its Expo dependencies as Gradle
projects, so those must be source-built too or configuration fails outright:

```
Build file 'node_modules/expo-task-manager/android/build.gradle' line: 19
> Project with path ':unimodules-app-loader' could not be found in project ':expo-task-manager'.
```

That is why `unimodules-app-loader` is in the list — `expo-task-manager` declares
`implementation project(':unimodules-app-loader')`. When adding a module, read its `android/build.gradle`
for `project(':…')` dependencies and add those as well. The failure is loud and immediate (configuration,
not compilation), so it is cheap to discover.

Cost: source-building these three turned a release build into ~13 min on a warm cache.

Two ways to confirm a build obeyed it:

- the Gradle log prints `[📦]` beside each module resolved from a publication — a patched module must
  **not** appear with that marker;
- grep the APK for the patch's marker string (below).

List which modules ship a publication with:

```bash
npx expo-modules-autolinking resolve -p android --json | grep -o '"publication"' | wc -l
```

## `expo-task-manager+57.0.12.patch`

Two changes: the delivery job is not persisted, and `TaskService` keeps one host while a task is
registered.

### `TaskManagerUtils`: the job is not persisted

`TaskManagerUtils.createJobInfo`: `setPersisted(true)` → `setPersisted(false)`.

Expo registers the background-location delivery as a persisted `JobScheduler` job. A persisted job
requires `RECEIVE_BOOT_COMPLETED`, and on some OEMs the persisted job crashed background location
outright. The only capability lost is a recording surviving a device reboot, which the app does not
promise. Designed in
`docs/design/specs/2026-08-22-onfoot-rn-record-activity-design.md` (§ the permission's
"belt-and-suspenders" note).

**If dropped:** background location may crash on affected OEMs, and the `RECEIVE_BOOT_COMPLETED`
permission in `app.config.ts` becomes load-bearing again.

**History (2026-10-04):** expo-task-manager also ships a prebuilt AAR, so until this date the patch
applied to `node_modules` without ever reaching the APK — the shipped behaviour was upstream's
`setPersisted(true)`. It is now genuinely live: the module is source-built, proven by the fact that the
build *failed* for a reason only a source build can produce (its `project(':unimodules-app-loader')`
dependency had no Gradle project). `adb shell dumpsys jobscheduler` shows the `TaskJobService` record
with no persisted flag, consistent with the patch. **Still worth a functional pass**, since this is the
first build in which the change takes effect: a recording should start, survive backgrounding and the
screen locking, and keep delivering batches.

### `TaskService`: one host while a task is registered

`TaskService` keeps the JS-facing task manager in one of two tables, `sTaskManagers` or
`sHeadlessTaskManagers`, chosen when the native module is created by whether the headless loader
holds a record for the app at that moment, which is a race. Upstream, `invalidateAppRecord` runs two
seconds after the last pending delivery finishes and removes the `sHeadlessTaskManagers` entry at
once, while the loader's own decision (destroy the host unless an activity is bound to it) runs later
on the main thread. With an activity bound, the host survives without its task manager: every
delivery is queued, none finishes, and the recording and every later one in that process stall.
Three hunks make an entry live exactly as long as its module. Designed in
`docs/design/specs/2026-11-14-recording-survives-process-death-design.md` (Causes 2, Solution 2).

| Hunk | Where | Does | Marker, logged each time it acts |
| --- | --- | --- | --- |
| keep-host | `notifyTaskFinished`, the delayed invalidate | skips the invalidate while the app has a registered task, so the headless host stays warm for the whole recording | `[onfoot-patch] TaskService keep-host: invalidate skipped, registered tasks=<n>` |
| invalidate-only | `invalidateAppRecord` | asks the loader to invalidate and leaves both tables alone | `[onfoot-patch] TaskService invalidate-only: invalidated=<bool>, …` |
| clear-both | `setTaskManager(null)`, from `TaskManagerInternalModule.onDestroy` | removes the entry from both tables; the only place an entry is removed | `[onfoot-patch] TaskService clear-both: task manager removed, foreground=<bool> headless=<bool>` |

keep-host logs once per delivery while recording, about every 8 s, foreground or headless: it is
the one marker on a hot path, kept because it is what shows the invalidate was skipped. On the device
(2026-11-15 spike, build C) keep-host and clear-both ran; the path invalidate-only closes was never
triggered there and is read from the source.

**If dropped:**
- **keep-host:** each delivery while the app is dead starts a host and the next invalidate destroys
  it. Each host leaks an `expo.modules.AsyncFunctionQueue` thread (`ncFunctionQueue` in `ps -T`) and
  about 3.3 MB, costs about 2.4 s of bundle load, and the long jobs exhaust the expedited-job quota
  (jobs every 40 s instead of 8 s under Doze with no foreground service).
- **invalidate-only:** a delivery finishing just after Pause or Stop (no task registered) drops the
  task manager while the activity keeps the host alive; the next recording in that process stalls.
- **clear-both:** a destroyed headless host leaves a stale weak reference in `sHeadlessTaskManagers`
  that nothing else removes once invalidate-only is in, so a later delivery can be handed to the task
  manager of a runtime that is gone, and never finish.

Not reported upstream yet: the owner files it (spec, Owner's calls).

## `expo-location+57.0.11.patch`

`LocationTaskConsumer.didReceiveBroadcast`: guard the `lastLocation` completion listener with
`task.isSuccessful` before reading `task.result`.

For a broadcast that carries no location result, the module falls back to
`mLocationClient.lastLocation` and reads `task.result` inside the completion listener. That listener
runs **after** `didReceiveBroadcast` returns, so the surrounding `try/catch (SecurityException)` is
no longer on the stack — and `Task.getResult()` rethrows the task's failure wrapped in a
`RuntimeExecutionException`. Once the user revokes the location permission, a delivery already in
flight therefore reaches the callback thread as an uncaught exception and kills the process.

Observed in the field as `FIELD-4` in `docs/reviews/2026-09-10-full-review.md` §5.1
(`SecurityException` at `LocationTaskConsumer.kt:89`, via `adb shell dumpsys activity exit-info` and
dropbox crash entries). The patch logs the failure the way the existing synchronous `catch` does and
returns, leaving the outer `try` in place for the throw that *can* still happen synchronously when
the `lastLocation` getter is called.

**If dropped:** revoking the location permission during or shortly after a recording can kill the
process instead of stopping capture cleanly.

Not reported upstream yet.

## `@gorhom/bottom-sheet+5.2.14.patch`

`BottomSheetContent` forwards `pointerEvents` to its draggable view.

`BottomSheet` renders its content with `pointerEvents="box-none"`, but `BottomSheetContent` drops the
prop, so the view carrying the content pan gesture takes touches over its whole box. That box is as
tall as the open snap point, and in `detached` mode nothing clips it: under the collapsed map card it
hangs through the bottom margin and off the screen. Gesture Handler's Android hit test enters
unclipped views (`GestureHandlerOrchestrator.kt`, `isClipping`), so a vertical drag that starts in
the margin under the card moved the card instead of the map. With `box-none`, the pan is recorded
only when the touch lands on the card's own views. Designed in
`docs/design/specs/2026-11-06-hiking-ux-design.md` (D74).

**If dropped:** a vertical drag starting in the margin under the collapsed card moves the card.

The marker is the component's `displayName`, `BottomSheetContent [onfoot-patch]`, a string in the
bundle (`strings` on `assets/index.android.bundle` in the APK). Not reported upstream yet.

## Checking a patch actually reached the build

A patch that applies to `node_modules` is not the same as a patch that is compiled into the APK — on
2026-10-04 a build made two days after the expo-location patch was applied still crashed at upstream's
line number, and nothing in the source tree explained it. So each patch carries a **marker string**
that exists only in the patched version, and a build can be checked rather than assumed:

```bash
APK=android/app/build/outputs/apk/release/app-release.apk
for d in $(unzip -Z1 $APK 'classes*.dex'); do unzip -p $APK $d | strings -a | grep -c '\[onfoot-patch\]'; done
```

A zero total means the build did not take the patch, whatever `node_modules` looks like. To tell the
markers apart (the `expo-location` one and the three `TaskService` hunks, one line each):

```bash
for d in $(unzip -Z1 $APK 'classes*.dex'); do unzip -p $APK $d | strings -a; done \
  | grep -oE '\[onfoot-patch\] (TaskService [a-z-]+|last location task failed)' | sort | uniq -c
```

A missing line names the patch or hunk the build did not take. The marker of
a native patch is also what appears in logcat when the guarded path runs, so the same string proves it
on a device:

```bash
adb logcat -d | grep onfoot-patch
```

A JS-only patch (`@gorhom/bottom-sheet`) is compiled into the JS bundle, not the dex, and its marker
(a `displayName`) is never logged, so neither check above sees it. Look for it in the bundle instead,
where Hermes keeps it in its string table:

```bash
unzip -p $APK assets/index.android.bundle | strings -a | grep -c '\[onfoot-patch\]'
```

Add a marker to any new patch, and keep it out of the hot path — it is a diagnostic, not a feature.
The one exception is a marker that is itself the evidence the path ran on every pass (`TaskService
keep-host`), and its entry says so.

## Upgrading a patched module

1. Bump the dependency. `postinstall` will fail loudly if a patch no longer applies — that failure is
   the signal, not a nuisance.
2. Read the module's new source at the patched site. If upstream fixed it, delete the patch and this
   entry.
3. If it is still broken, regenerate: edit the file in `node_modules`, then
   `npx patch-package <module>`, and delete the old patch file (its name carries the old version).
   Once a native build has run, the module holds an `android/build` folder: add
   `--exclude '(^|/)build/|package\.json$'`, or the patch carries the build outputs.
4. Native changes are device-verified — none of the patches is reachable from Jest.
